# 案件ボード（自動整理）設計と運用

「普段どおり仕事をするだけでボードが更新され、判断できない事項だけまとめて確認する」ための仕組みです。
案件ごとの日報・進捗入力は前提にしていません。

## 全体構成（役割を分離）

```
情報源（Gmail / Google ドライブ ほか）            ← 初期版は読み取り専用
        │ 取得（差分のみ）
        ▼
 同期ジョブ（取得 + AIによる整理）   docs/sync-job-prompt.md
        │ 取得結果（JSON バッチ）
        ▼
 Worker  /api/pm/ingest   … 検証・紐づけ・重複排除・根拠確認・人の修正の保持
        │
        ▼
 Cloudflare D1（保存）  ── Worker /api/pm/*  ── 画面 public/board.html
```

| 層 | 役割 | 実装 |
|---|---|---|
| 情報取得 | 新しい情報・変更だけ取得 | 同期ジョブ（下記） |
| AI処理 | 依頼・決定・実施・待ち・残作業を抽出 | 同期ジョブ（下記） |
| 反映ルール | 重複排除、根拠必須、矛盾は確認へ、人の修正を保持 | `src/pm/engine.js`（AIを使わない決まったルール） |
| 保存 | 台帳・活動記録・状況・タスク・提案・確認事項・履歴・同期状態 | D1（`migrations/0002_project_board.sql`） |
| 表示 | ボード・案件詳細・確認一覧・設定 | `public/board.html` |

AIの出力は「提案データ」として扱い、Worker側のルールで検証してから保存します。
資料やメッセージ内の命令文は、システムへの指示として扱いません（データとして保存されるだけ）。

## 情報源：確認できたこと／できないこと

2026-10-01 時点の、この環境での確認結果です（**接続・権限を確認できたものだけ**を「利用可」としています）。

| 情報源 | 状況 | 備考 |
|---|---|---|
| Google ドライブ | 利用可（接続済み・フォルダ一覧とファイル読み取りを確認） | 案件フォルダの `AGENTS.md` / `README.md`（現在の状態）/ `DECISIONS.md`（決定事項）は正本として優先できる。共有ドライブ上の案件は、権限を要確認 |
| Google Docs / Sheets | ドライブのコネクタ経由で内容を読める見込み（未検証） | 対象案件が決まったら検証 |
| Gmail | 接続済み。ラベル一覧の取得を確認 | **どのラベルが案件対象かは利用者の指定が必要。** 予約システムの自動通知など、お客様の個人情報を含むメールは対象外にする |
| 業務チャット（Slack 等） | **利用不可**（接続済みコネクタにない） | 必要なら接続を追加 |
| 会議の議事録・文字起こし | Zoom・カレンダーの接続を確認。**議事メモ(Gemini)は主催者のドライブにあり、共有されていないと開けない** | 要約・文字起こしを取得できる会議だけが対象。取得できない会議は「要確認」として表示する |
| Google カレンダー | 利用可（予定の日時・参加者・添付の有無） | 予定は活動記録として扱う（タスクにはしない） |
| 既存のタスク管理ツール | **利用不可**（Notion は接続が未完了） | 接続を完了すれば候補 |
| AIとの作業履歴（会話履歴） | **取得できない（制約）** | 代替: 作業終了時に要約を案件フォルダへ自動保存する運用（下記） |
| 案件フォルダ内の制作物・作業記録 | ドライブ経由で利用可 | ファイルの更新だけでは完了にしない |

### AI作業履歴の代替
会話履歴そのものは取得できません。代わりに、AIが作業を終えるときに
`01_資料/作業記録/YYYY-MM-DD.md` へ要約を保存する運用にすると、ドライブの更新として自動で拾えます
（利用者の転記は不要）。テンプレートの `AGENTS.md` への一行追加が必要なため、**変更は承認後**に行います。

### 収集しないもの（初期設定）
- 取得は「案件に対応づけたフォルダ・ラベル」だけ（許可リスト方式）。
- さらに除外リスト：ファイル名に `recovery` / `password` / `secret` / `token` / `tfa` / `パスワード` / `認証コード` を含むもの。除外するフォルダ名・送信元・ラベルは、各自の環境に合わせて設定画面（または `local/setup-initial.mjs`）で登録する。
- 設定画面（案件ボード → 設定）で変更できます。

## 同期ジョブ（取得 + AI整理）

推奨は **Claude の定期実行（クラウド）+ 接続済みコネクタ** です。

- 採用理由：Gmail / ドライブはすでに接続・認証済みで、Google Cloud の設定や APIキー管理が不要。PCを閉じていても動く。
- 取得は読み取り専用。返信・編集・広告設定の変更はしません。
- 結果は JSON バッチで `POST /api/pm/ingest`（Bearer トークン）へ送るか、D1 の `pm_batches` に追加します。Worker が15分ごとに反映します。
- 制約：実行間隔は最短1時間、Claude の利用枠を消費する、実行環境から Worker の URL へ接続できる必要がある（できなければ D1 経由）。**この接続経路はデプロイ後に実測して確認します（未検証）。**

代替案：Worker 内から Google API と Claude API を直接呼ぶ構成。完全に自前で時間指定も自由ですが、
Google Cloud のOAuth設定・リフレッシュトークン管理・APIキー管理が必要で、初期設定の負担が大きいため、初期版では見送りです。

手順書とAIへの指示文は [`docs/sync-job-prompt.md`](./sync-job-prompt.md) にあります。

## 反映ルール（`src/pm/engine.js`）

| ルール | 動作 |
|---|---|
| 根拠必須 | 根拠（出典・箇所・日時・引用）のない項目は保存しない |
| 期限・担当 | 根拠の引用があるときだけ採用。ないものは採用しない |
| 完了 | 明確な完了記録（`explicit_record`）またはタスクツールの完了状態（`tool_state`）のみ自動で完了。ファイル更新だけでは完了にせず、確認事項へ |
| 制作完了/先方承認/公開完了 | `milestones` として別々に、根拠がある場合だけ記録 |
| 重複 | 正規化した文言の一致＋類似度で同一判定。複数の情報源は1件にまとめて根拠を追加。再処理しても増えない |
| 変更・取消 | 明示された変更（`explicit_change`）・取消は反映。取消済みは復活しない |
| 矛盾 | 自動で上書きせず確認事項に。同じ不明点は一度しか聞かない（回答・却下後も再作成しない） |
| 人の修正 | 手動で変更した項目は保持し、矛盾する新情報は確認候補にする |
| 取得失敗 | 最後に取得できた情報を保持。タスクの完了・削除はしない。失敗・情報が古い状態を画面に表示 |
| 紐づけ | 台帳の対応（フォルダ・ラベル・スレッド）を優先。特定できなければ未分類、複数案件なら確認へ。回答はスレッド/フォルダ単位で学習 |
| 提案 | 確定タスクとは別に保存。採用/保留/却下で扱い、却下・保留した提案は再提案しない |

## 保存データ
`pm_projects`（案件台帳）、`pm_project_links`（案件と情報源の対応）、`pm_sources`（同期状態）、`pm_activities`（活動記録と出典）、
`pm_project_state`（現在の状況）、`pm_tasks`（確定タスク）、`pm_suggestions`（AI提案）、`pm_decisions`（決定事項）、
`pm_review_items`（確認事項）、`pm_change_log`（更新履歴）、`pm_batches`（取り込み待ち）、`pm_settings`（設定）。

## アクセス管理・データの扱い
- ログイン：`APP_PASSWORD`（編集可）、`APP_VIEWER_PASSWORD`（閲覧のみ・任意）。いずれも Worker のシークレットで管理。
- 取り込み：`INGEST_TOKEN`（Bearer）。取り込みと同期設定の読み取りだけができ、ボードの閲覧・編集はできません。
- 認証情報・APIキーは Worker のシークレット／同期ジョブ側で管理し、画面やリポジトリには置きません。
- 保存するのは本文の全文ではなく、**短い引用（既定200文字）**と出典。保存日数（既定180日）を過ぎた活動記録と引用は自動削除（15分ごとの定期処理）。
- AIへ送る範囲（項目・本文の最大文字数・除外情報）は設定画面で指定し、同期ジョブが取得時に参照します。**AI処理は同期ジョブ側で行われるため、この範囲の遵守はジョブへの指示によるもので、Worker側で技術的に強制できません。**

## 概算の運用費
前提を置いた概算です（為替 1ドル=150円、単価は Claude Sonnet 系 入力$3/出力$15 / 100万トークン、Haiku 系 入力$1/出力$5 を仮定。**最新の単価は要確認**）。

- Cloudflare（Workers + D1 + 定期実行）：この規模なら無料枠内で **0円/月**。
- AI処理を Claude API で行う場合（案件3つ、平日9〜19時に1時間ごと = 月約240回、差分のみ処理）
  - 1回あたり 入力 約8,500 / 出力 約1,200 トークンと仮定 → 月 入力 約2.1M / 出力 約0.3M
  - Sonnet 系：約 **1,600円/月**、Haiku 系：約 **530円/月**
  - 情報量が5倍になれば、およそ5倍
- 推奨構成（Claude の定期実行）の場合：API費用は発生せず、Claude の利用枠を消費します。利用枠への影響は実測して確認が必要です。

## 実データでの確認から分かったこと（一般化した内容）
具体的な案件名・フォルダ・メール内容は、公開リポジトリに含めません。

- 案件によって「状況の正本」が違う。人が書く議事・メールが中心の案件と、承認・納品の記録（台帳）が正本の案件がある。
  後者は、台帳の記録そのもの（承認の有無・納品・出稿）から状態を決まったルールで計算する専用の取得処理が有効。
- 自動通知メール（予約・広告・システム通知）が大半を占める案件がある。これらは案件管理に不要で、個人情報を含み得るため、送信元・ラベルで除外する。
- 日々自動生成されるレポート・動画・実行ファイルは、内容を読まずに更新の事実だけ記録する（`metadata_only_patterns`）。
- 議事メモは主催者側のアカウントに保存され、共有されていないと取得できない。取得できない会議は、確認事項として「共有の依頼」を出す。
- 資料に明記された依頼・期限・担当が少ない案件では、タスクは増えず、決定事項・状況・確認事項が中心になる（推測でタスクを作らないため）。
